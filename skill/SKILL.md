# 场景流程工坊

## 调用条件

用户要为某个场景生成流程时调用。输入：场景名 + 场景真实输入（行业现成做法、用户经验、真实规范）。
场景真实输入缺失时，不停止、不编造：先出骨架，把缺失处标“待定”，等用户或真实资料补。

## 生成方法（固定五步，不换顺序）

### 1. 写行业 SOP

这个行业的人现在是怎么做这件事的？填这张表，流程骨架就出来了：

| 步骤 | 谁干 | 输入 | 产出 | 下一步交给谁 | 备注（容易错的地方） |
| --- | --- | --- | --- | --- | --- |
| 1 | | | | | |

填表规则：
- 一步只干一件事，产出要具体（是一份文档、一个决定、一张图，不要写“处理一下”）。
- 每一步的“下一步交给谁”必须写明，不能出现没人接的产出。
- 容易错的地方单独记，后面变成护栏。

### 2. 拆角色和节点

每个角色一张卡，照着填：

- **role（角色）**：这个角色是谁。
- **goal（目标）**：要达成的结果，一句话。
- **backstory（背景）**：经验和行事风格，两三句，决定它说话和判断的方式。
- **输入**：接什么（上一步的产出，具体格式）。
- **输出**：交什么（具体格式，含期望产出标准）。任务必须写期望产出，不能只写干什么。
- **工具**：能用什么（没有就不写）。
- **终止条件**：什么时候算干完、什么时候必须停（产出达标、循环到上限、触发红线）。

节点写法（按需选用，不混用）：
- 固定步骤走固定顺序（死的步骤不经模型判断）。
- 需要判断的步骤让模型选下一步。
- 复杂任务先出计划再按计划执行。
- 角色之间不直接调用，只靠订阅接力：每个角色只订阅自己需要的上游产出，订阅依据是上游产出的来源；上一步产出必须写进一个具名状态，下一步引用名字取用，不要把上文全贴给下一个。
- 讨论会诊型场景用群聊 + 终止条件：终止条件单独列出、可组合（“或”“与”）、每轮自动重置；评审说约定短语（如“通过”）即停。

### 3. 标人工验收点

高风险、不可逆、质量红线的地方，必须有人看一眼才能往下走。验收点要同时做到两点：
- 画在流程图上（符号 `◎ 人工验收`），不能藏在步骤里。
- 写成任务的一个显式开关（开/关），执行时才不会漏掉。
- 可改的产物（提示词、图等）：先过目、可人工修改调整、再往下走。
- 不可逆的动作（对外发布、提交、下单、给结论）：必须有人拍板才能执行。

### 4. 加护栏

每个场景的流程都要过一遍这张清单，缺的补上：

- [ ] 禁区清单：这个场景绝对不能做的事。
- [ ] 事实核对点：数字、规格、名称这类事实由谁核对（不能只靠模型自己说）。
- [ ] 触发红线怎么办：拦下转人工，还是退回上一步重做？
- [ ] 循环上限：返修最多几轮？到了上限怎么办（转人工还是按现有结果交）？
- [ ] 终止条件：除循环上限外，还有哪些停的条件（关键词即停、预算耗尽、超时、交接转人工）？
- [ ] 出错回退：某步失败了，整个流程停在哪、从哪一步重跑？
- [ ] 产物落盘：每步的产出是否都留下来可查（不能黑盒一次到底）？
- [ ] 预算：token 或费用预算是多少？耗尽即停。

### 5. 先跑最小流程验证

先跑通最简版本再加复杂度。纸面推演（无模型 Key 时也照此做）：
- 用一个通用示例从头到尾走一遍流程。
- 查三样：死循环、缺验收点、缺终止条件。
- 有问题先修流程，再加复杂度。不要一上来就堆满角色和分支。

## 流程图记法

- `[节点]`：一个步骤（对应一个角色或一个固定动作）。
- `──►`：流转，下一步。
- `◆ 条件？ ──是──► / ──否──►`：分支，按条件走不同路。
- `↻ 最多 N 轮`：循环返修，标清上限，防死循环。
- `◎ 人工验收`：人看一眼、可改、通过了再往下走。
- `■ 红线`：触发即拦下，转人工，不再往下走。

## 宽容度规则（全场景通用）

- 验收分三级：通过 / 可修补（后期可补的不返修重做）/ 返修（结构性问题必须返修）。
- AI 生成类产物（生图等）变形、细节漂移属预期内，可修补的走后期补足，不因为小瑕疵反复返修；结构改不了的才返修。
- 每种缺陷都要定级：写清判定标准 + 处理方式。返修必须对应到返修分类（构图类 / 产品类 / 文字类 / 风格类等），不写原因的返修不接。
- 每个实例的宽容度分级表、检查表、模板、返修分类、常见错误都要有；不能编造的阈值标“待定”，等用户经验或行业数据补。

## 角色卡提示词写法

按这个固定顺序写角色提示词：身份（目的、风格、目标）→ 指令（规则、能做什么、绝不能做什么，含禁区清单）→ 示例（输入和期望输出，示例要覆盖多样输入）→ 上下文（私有数据、参考资料，放最后）。
- 结构化输出用 JSON Schema 约束，不要只靠文字描述。
- 长流程的角色加两条：持久性指令（一直做到完全解决再交还控制权，拆成子任务、每步确认完成）+ TODO 跟踪（防漏步骤）。
- 提示词改了要能回测：产物落盘，改动可对比，不口头觉得变好了。

## 输出格式（每个实例统一）

1. 流程图（文字版，按上面记法）。
2. 角色卡（role / goal / backstory + 输入 / 输出 / 工具 / 终止条件）。
3. SOP 步骤表。
4. 细则层：宽容度分级表、检查表、模板、返修分类、常见错误。
5. 验收点和护栏清单（含待定项）。
6. 演示示例：用一个通用示例纸面推演一遍，标注“演示，非真实执行”。

## 交付前自查（评审清单，逐项打勾）

- [ ] 流程闭环：每步有输入、产出、下一步交给谁，无没人接的产出。
- [ ] 角色卡齐全：role / goal / backstory + 输入 / 输出 / 工具 / 终止条件。
- [ ] 验收点标明：画在图上 + 写成显式开关。
- [ ] 护栏齐全：禁区清单、事实核对点、红线处理、循环上限、终止条件、出错回退、产物落盘、预算。
- [ ] 宽容度分级：每种缺陷定级 + 判定标准 + 处理方式；结构性问题必须返修。
- [ ] 事实核对：数字、规格、名称有来源；提示词里无凭空编造的规格；不能编造的标待定。
- [ ] 引用状态：引用的仓库 / 文档标注核实状态与时间；未核实项不当定论。

## 引用条件（什么能当参考、什么不能）

- 能当参考：标注“已核实”的官方文档、仓库页、API 数据；star 数以标注日期为准，之后会变动。
- 不能当定论：标注“未核实”的项；声明未展开的部分；star 数、版本号等时效性数据过期后须重核。
- 改动规则：改方法先改评审标准；改实例须同步改检查清单与护栏，不得只改流程图。

## 模型说明

- 现阶段无外部模型 Key 时，用执行者自身能力顶上（写提示词、做检查、做纸面推演）；后续补 Key 后，同一流程直接换模型执行，流程本身不变。
- 真跑验证需要能裸调的文本模型 Key；没有时，纸面推演先行，真跑后置。
